## [Unreleased] today

### Added
- An inbox at the top of the landing page (`pages/Landing/LandingInbox.tsx`, `lib/inbox.ts`). It lists the tasks mail made that nobody has opened, newest first, each with its project and when it arrived; five show until **Show all**. A row opens the task in the edit dialog on the landing page itself, and opening it is what takes it out of the inbox (`viewed_at`, as before). It replaces the **New tasks** filter row: the inbox is not a filter, and the board shows those tasks wherever the rows below put them.
- Admin has a **Goals** card (`pages/Admin/GoalSection.tsx`) beside Projects and Owners: every goal on the board and in the archive, open ones first, with its project, its building-block count and, for a closed one, its stage or "Archived". Archive closes a goal (the task archive endpoint, so the history records it) and Reopen brings it back; building-blocks stay where they are.
- A landing page that chooses what the board shows (`client/src/pages/Landing`). `/` is now the landing page and the board moved to `/board` (`ROUTES.HOME`, `ROUTES.DASHBOARD`). Its rows are Project, Goal, Owner, Due by, Stage and New tasks, each a multi-choice read from the board's own data with counts across the whole board; nothing ticked in a row means the row does not filter, and a "Showing N of M" line counts exactly what the board will show. GO opens the board. The choice is kept per browser (`kanban-board-filters`, `hooks/use-board-filters.tsx`): one project is still the header's project scope, two or more stay in the filters with the scope at All projects. Due by: "Not done before" is open work due on or before a date, "Archived before" brings archived tasks due by then onto the board in the columns they fill. Choosing a closed stage (Done) draws its column. New tasks are tasks mail made that nobody has opened: a new `tasks.viewed_at` (migration 0024; existing rows and every other way in count as seen), stamped by `POST /api/tasks/:id/viewed` when the task dialog opens. The board's owner and goal filters, the More menu, the goal picker, the project selector and the filter chips all read the same choice; the logo and a Change pill lead back to the landing page.
- The inbox: mail (and notes) become tasks without a mail provider's API (`INBOX_SETUP.md`). `POST /api/inbox` takes a raw email (`message/rfc822`, parsed on the server with mailparser: headers and text body, quoted replies cut off, HTML converted, attachments dropped), a note (`text/plain`, first line the subject) or JSON (`subject`, `text`, `from`, `to`, `messageId`), queues it in `inbound_email_processing` and answers `202 { id, duplicate }` at once, so the thing that receives mail for the domain (a Cloudflare email worker, an inbound-parse service, a forward rule, a phone shortcut, a script) only ever makes one HTTP call and any of them can replace any other. A redelivery answers with the row it already has: inbox rows are keyed by the RFC Message-ID or a digest of sender, subject and text. The route is opened by a third credential the developer console issues, an **inbox token** (`kbi_…`, `Authorization: Bearer`), which opens that one route and nothing else and is hashed under its own purpose so it can never pass for an export token or the reverse; `INBOX_ALLOWED_SENDERS` is a second gate for mail, whose From anyone can forge. The inbound worker reads an inbox row from the row itself (the Gmail pipeline's rows are still fetched from Gmail) and makes the tasks one of two ways, chosen by `INBOX_EXTRACTION`: `plain` (subject as the title, text as the description, no model) or `llm` (the existing LangGraph extraction); unset, the model is used when `OPENAI_API_KEY` is set and the plain reading otherwise. In either mode `!high` (or `!low`, `!normal`, `!critical`) and `@in-progress` in a subject set the priority and the stage and leave the title. `inbound_email_processing.gmail_message_id` is renamed `message_key` and gains `sender`, `subject` and `body_text` (migration `0023`). The Gmail pipeline is unchanged and feeds the same queue; `GMAIL_INBOUND_WORKER_DISABLED` now stops the inbox too.
- "Make this a goal" (`GoalPlanDialog`, `shared/goal-plan.ts`): on a saved task whose type is Goal, the task form's button asks an OpenAI model to break the goal into building-blocks, and nothing is sent until **Plan this goal** is pressed. Two options shape the request. **Help me on the how** asks for plain-language, physical step-by-step descriptions (up to 20 sub-tasks, one layer deep, each a list of numbered actions and a line on why). **Help me on the who and where** turns on OpenAI's `web_search` tool to fill each sub-task's contacts (name, purpose, phone, email, official page, address and the source URL it was read from), assuming New Zealand unless the task says otherwise and leaving a detail null rather than inventing it. The plan dialog offers suggested goal wording, applied only if ticked, and editable rows (title, description, effort, and what each waits for among the suggestions and the goal's existing blocks), saved one at a time, ticked or all through `POST /api/tasks/:id/goal-plan/apply`: one transaction creates the blocks with the goal's project and owner in the first backlog column, adds their dependencies under the existing database rules, and appends any contacts to a block's description as a "Who and where" section marked check before relying on it. Unsaved changes, an unsaved task or a type other than Goal stop it with a toast before any network call, and the server repeats the type check. The call uses the OpenAI SDK's Responses API with a strict JSON schema (`responses.parse` + `zodTextFormat`; 150 s timeout with web search, 60 s without) rather than LangChain, because web search and structured output have to share one request. Admin gains an **AI assistant** card: a model picker limited to GPT-5 and later (the models the saved key can use, read from `/v1/models`, or a documented list without a key), defaulting to `gpt-6.1-sol`, with any other model id refused by the server; and an API key that is checked against OpenAI before it is stored, kept AES-256-GCM encrypted in a new `app_settings` table (migration `0021`) under `SETTINGS_SECRET` or, without one, a key derived from `DATABASE_URL`, never sent to the browser (only its last four characters are shown), and backed by `OPENAI_API_KEY`. A saved key that a changed secret can no longer read is reported in Admin and asked for again.
- An access gate (`server/access/`). Every `/api` route answers only a browser that has been admitted, except `/api/health`, `/api/access/*`, the Gmail Pub/Sub webhook (which keeps Google's signed-token check) and `GET /api/export` with a live **export token**. A browser is identified by 256 random bits in an HttpOnly, SameSite=Lax cookie (`__Host-` and Secure in production) and admitted by an **access code** (`KB-XXXX-XXXX-XXXX`, 60 bits, no I, O, 0 or 1) issued for it and shown once. A code binds to the first browser that enters it and trusts that browser for 90 days, renewed by entering it again; unknown, revoked and another browser's codes all get the same 403, and admission is rate-limited to 10 per 15 minutes per address. The client shows an access-code screen until the browser is admitted, and again on any `access-required` 401. An **export token** (`kbx_…`, sent as `Authorization: Bearer`) opens `GET /api/export` and nothing else, for the briefing agent. Cross-site writes are refused before they are read (`Sec-Fetch-Site`, `Origin`). Codes and tokens are issued, listed and revoked in a **developer console** at `/console` (API `/console/api`, `client/src/pages/Console.tsx`), which answers only with `DEVELOPER_SECRET` in `x-developer-secret`, compared in constant time, answers anything else exactly like an unknown address, and is rate-limited to 60 per 15 minutes. Codes, tokens and browser keys are stored only as HMAC-SHA-256 digests under `CODE_HASH_KEY`, in a new `access_devices` table (migration `0022`). Production refuses to start without `CODE_HASH_KEY` (32+ characters) and `DEVELOPER_SECRET` (16+), and the start-up error names each failing variable and whether it is missing, empty or too short after trimming, never its value; locally, with no `CODE_HASH_KEY`, the gate is off.
- Select and edit tasks together. A plain mouse drag on empty board space draws the selection box; a click without movement still clears the selection, dragging a card still moves it, and Shift+drag adds to the selection from anywhere. With tasks selected a bar offers **Edit together**, **Share** and **Clear** (Esc clears too). **Edit together** (`BulkEditDialog`) sets one field (stage, project, priority, type, goal, owner, effort, due date or recurrence) on every selected task through `POST /api/tasks/bulk-update`, in one transaction or not at all: each task goes through the same rules as a single save (the goal-link, owner, project and dependency triggers), the task that breaks one is named, and stage moves write the usual history line. Giving untyped tasks a goal makes them its building-blocks; a task that is itself a goal is refused. A **goal filter** beside the project filter narrows the board to one goal in the current scope and its building-blocks, and combines with the owner, warning and search filters.
- Project and goal views (`client/src/pages/Goals`, `shared/goal-view.ts`, `shared/schedule.ts`, `shared/plan-summary.ts`). `/projects/:projectId` (`none` for no project) lists every goal in the project with its progress (building-blocks done) and the days of dependent work left. `/goals/:goalId` lists the goal's building-blocks in dependency order with what each waits for, and works the plan out on demand in two views. **Critical path** is a network diagram: cards in columns by how much dependent work comes before them, the critical chain in the accent with a slow flowing dash that stops under `prefers-reduced-motion`, slack cards outlined, done cards dashed, Today and Finish pills, a legend, and every card a keyboard button that opens the task. **Gantt** draws the same schedule in the same colours, with due dates as diamonds that turn red when the schedule lands after them. A block that waits for work outside its goal is marked "starts after" in the list, on the diagram and before its bar, amber while that work is open; the goal's dates still come from its own blocks only. Under both views a write-up built from the same schedule (headline, the chain that sets the date, what can slip and by how much, what can run side by side, missed due dates, unfinished outside waits, then each step) keeps the text and the picture from disagreeing. The schedule is the critical-path method over the goal's own dependencies; a task has no duration, so effort counts as days (none is 1, finished is 0), the plan starts today and weekends are not skipped. Nothing new is stored.
- The board says what is narrowing it (`describeActiveFilters`, `pages/Dashboard/active-filters.ts`): a read-only strip names the project, owner ("Everyone" is stated) and goal scope and, while they are on, the pressed warning, the search query and focus mode, highlighting the values that narrow and muting the defaults.
- Goals, building-blocks and dependencies. A task may have a **type**, `goal` or `building-block` (nullable `tasks.type`, migration `0016`; existing tasks stay unset). A building-block can name the goal it contributes to (`tasks.goal_task_id`, migration `0017`), and any task can have **predecessors** and **successors** (`task_dependencies`, one edge per row in one direction, migration `0018`), picked in the create and edit forms and sent as `predecessorIds`/`successorIds` on task create and update, where a side that is present replaces that side. `GET /api/task-dependencies` lists the edges, and the export carries an optional `dependencies`. The database enforces the rules: a goal link points at a goal, no task depends on itself, the graph stays acyclic (trigger), a building-block shares its goal's project unless the goal has none (migration `0019`), and an edge joins two tasks in the same project, no project counting as a project of its own (migration `0020`). `shared/task-goal.ts` and `shared/task-dependencies.ts` repeat the rules so a breach is a 400 that says why rather than a database error. Rows written before `0019` and `0020` are checked the next time they are touched, and moving a goal or a task to another project is refused while its links would break, rather than moving them along. The pickers offer only tasks that fit, drop links that stop fitting when the project changes (with a note), and are disabled with the reason when the task is a goal, whose order comes from its blocks; the API still accepts a goal's dependencies. Import does not restore goal links or edges.
- Owner is an entity, and a person's lane is that owner (EPIC-06). `tasks.owner` was a free-form `varchar(15)` with no table and no foreign key, whose set of valid values was whatever `SELECT DISTINCT owner FROM tasks` returned — so a typo invented a person, a rename was impossible, a person stopped existing when their last task was binned, and "this is Rich's" could be stored three ways at once (the field, plus a lane tag per stage). There is now an `owners` table (`name` unique case-insensitively in the database, optional short `key`, `color`, `archived`, `order`) and a nullable `tasks.owner_id` (FK, `ON DELETE SET NULL`, indexed with `stage_id`); null is "Unassigned". A sub-stage also carries a nullable `owner_id`: a lane bound to an owner holds exactly the tasks in its stage that owner owns and reads nothing from `tags`, so dropping a card into it is the assignment, dragging a card out of it onto the column clears the owner, moving a task to another stage lands it in that owner's lane there, and a stage may hold at most one lane per owner (409). Every other lane matches tags exactly as before, and an unlaned task falls into the first lane that is nobody's rather than being claimed by a person's. Admin gains an Owners card (create, rename, recolour, archive/unarchive, delete — deleting releases their tasks and unbinds their lanes), and a sub-stage can be bound to an owner there. The owner picker offers only owners that exist — free-text creation is gone — and hides archived owners unless the task already has one. Cards, the preview pane and the lane headers take their name and colour from the row, with the short code standing in on a card when the name is longer than 15 characters; the More menu filters the board to one owner (or to the unassigned) and sorts cards by owner name. Migration 0013 backfills with the lane winning any disagreement, records every overwrite in `owner_backfill_report`, aborts rather than guessing where a board is ambiguous, strips only the tags of bound lanes (topic tags survive), and keeps `tasks.owner` as a trigger-maintained mirror of the owner's name so `GET /api/export` and the daily-briefing agent keep reading the field they read before; `shared/briefing.ts` loses the heuristic that guessed which lanes named people, and `ownerConflict` is false by construction. New `GET/POST /api/owners`, `PATCH/DELETE /api/owners/:id`; a task write naming an owner with no row is a 400. `GET /api/tasks/owners` still answers with the names, for the consumers that read it. Imported tasks are matched to owners by name, and names this board does not have are reported rather than created.
- The board warnings filter the board: pressing Overdue, High-priority waiting, Many in progress or Stale tasks shows only those tasks, and pressing it again clears it. A pressed warning carries `aria-pressed` and is washed and ringed in its own tone. The four rules moved out of the component into `shared/board-warnings.ts`, so a count and its filter cannot drift, and counts come from the whole board, so a number does not move under its own filter. The warning, owner and search filters narrow together.
- Task attachments are rows, not base64 in the description (EPIC-03 story 7). A file attached to a description is uploaded on its own (`POST /api/attachments`, raw body ≤ 10 MB, type and name in headers) into a new `task_attachments` table (`task_id` FK `ON DELETE CASCADE`, `filename`, `mime_type`, `byte_size`, `data bytea`; migration 0011), and the description's chip references it by `/api/attachments/:id`. Saving a description binds the rows it references to the task and releases the ones it dropped; rows no saved description has referenced for a day are swept (at startup and hourly). A chip pasted from another task's description gets its own copy of the file, so deleting either task never breaks the other. `GET /api/attachments/:id` serves the file with `Content-Disposition` (inline for images, PDF, audio, video and plain text; always a download for anything else and for SVG), `X-Content-Type-Options: nosniff`, a `default-src 'none'` CSP (not on PDFs, whose viewers need it off) and immutable caching; `?download=1` forces a download. On first start after the upgrade every description still holding a file inline is rewritten to reference a row, without touching `updatedAt`; import files from before the change are handled the same way on save. The export lists each task's attachments (`attachments[]`, `counts.attachments`) and embeds their bytes with `?includeAttachments=true`, which the board's Export and Share use, so an import restores files by uploading them here first. Shared allow-list, size limit and chip helpers live in `shared/attachments.ts`.
- Project layer (EPIC-01): a project is a set of tasks related to a common goal, and the board can be scoped to one at a time while every stage and sub-stage stays exactly as it is. New `projects` table (`name`, optional short `key`, `color`, `archived`, `order`) and a nullable `tasks.project_id` (FK, `ON DELETE SET NULL`, indexed with `stage_id`); existing tasks need no backfill — a task with no project is simply "unassigned". Admin gains a Projects card (create, rename, recolour, archive/unarchive, delete — deleting releases the project's tasks rather than removing them). A project selector appears in the board header as soon as one project exists, offering "All projects", each active project with its live task count, and "No project"; the choice is filtered server-side (`GET /api/tasks?projectId=<id>|none`, same on `/api/tasks/archived`), applies to Filing and Archive but not Admin, persists per browser (`localStorage` key `kanban-project-scope`) and is mirrored into `?project=` so a scoped view can be shared by link. New tasks land in the project being viewed; the create and edit forms carry a Project field (hidden until a project exists). Under "All projects" detail cards, summary hover cards, Filing and Archive show a colour-dot project chip, which disappears when the header already names the project; the preview pane always names it. Imported tasks keep a `projectId` this board knows, otherwise they land in the project being viewed. New `GET/POST /api/projects`, `PATCH/DELETE /api/projects/:id` (409 on a duplicate name, case-insensitive). Shared `shared/project-scope.ts` holds the scope tokens both sides read and write.
- Search reveals its result: while a query is active the board scrolls the first matching card into view (`scrollIntoView`, nearest edge, smooth unless `prefers-reduced-motion`) — through the page in the vertical layout, or the column/strip in the horizontal one — and previews it in the pane, so a hit that sits below the fold or in a scrolled column is not missed. Fires once per query and match, never mid-drag.
- Task preview pane in the horizontal board layout (`TaskPreviewPane`): a full-height, read-only view at the end of the stage row showing the whole task — stage and lane, title, status/priority/effort/owner/recurrence, due date with overdue/today flags, the complete rich-text description, tags, created/updated/parent, and recent history — with an "Open task" button. It follows whichever card the pointer rests on (250 ms hover intent, so crossing cards on the way to the pane leaves it alone), or the last card pressed, clicked or keyboard-focused, and keeps that task until another is chosen. Never changes during a drag or marquee. Resizable against the last column; its width persists under the `preview` key in `kanban-column-weights`.
- Voice dictation on every free-text task field (title, description, owner): a mic button starts the browser's Web Speech API — Apple's recogniser under macOS Safari — shows an animated sound wave and live interim words while listening, and inserts finalised phrases at the caret (`useSpeechDictation`, `DictationButton`, `VoiceInput`, `lib/dictation.ts`). Browsers without the API fall back to focusing the field and pointing at macOS Dictation.
- "Share" in the task view copies the task to the clipboard as a formatted, paste-ready email in both plain-text and HTML flavours (`lib/task-email.ts`, `lib/clipboard.ts`). Clipboard only — no mail client is contacted and no `mailto:` link is produced.
- Resizable board columns in horizontal layout: drag (or arrow-key) the gutter between two stages to change their split, double-click a gutter to even the pair out, and "Reset widths" next to the archive strip clears every override. Widths are stored per stage as flex weights in `localStorage` (`kanban-column-weights`), so the board stays proportional at any viewport width.
- `GET /api/export` returns the board as a single JSON object (`shared/export.ts`): stages, sub-stages, projects and tasks plus `formatVersion`, `exportedAt`, `scope` and `counts`. Supports `?includeArchived=true` and `?projectId=<id>`, which scopes the exported tasks to one project (`scope.projectIds` names it; `projects` is always listed in full so a scoped file stays self-contained). A non-numeric `projectId` is a 400.

### Changed
- Project and Goal no longer read as the same thing. Each row of the landing page now has one plain line under its label saying what it is: **Project** "A body of work, like a client or a job", **Goal** "An outcome, with the tasks that lead to it" (once a project is ticked: "Outcomes in the projects you ticked, with the tasks that lead to them", since the row only lists goals inside them), **Owner** "Who the task belongs to" and **Stage** "Which column the task sits in". The line describes its row for a screen reader too (`FilterRow`'s new `hint`). Admin → Projects drops "A set of tasks with a common goal" for the same definition, and the README, `ARCHITECTURE.md` and code comments follow: a project holds tasks, and a goal is one of those tasks, so the order is project → goal → building-blocks.
- `npm run check` is the whole pre-merge gate, and it passes. It now runs the type-check (`npm run typecheck`, `tsc --noEmit`) between lint and the format check; it never had, so a test fixture's type error sat on `main` from #131 until now. Run from the main checkout, Vitest no longer also collects the Claude Code worktrees under `.claude/`, which had put four copies of the suite, integration tests included, on one database. The supertest-based tests serve their app on 127.0.0.1 (`server/test-support/loopback.ts`) instead of letting supertest bind `::` and dial 127.0.0.1, which on macOS let a request reach another test process's server, be reset or hang when suites ran side by side. The LangGraph test that checked parallelism with a 160 ms wall-clock bound now counts the steps in flight. The tracked Railway log export `logs.1774761325491.json` is gone and `logs.*.json` is ignored.
- The board is filtered in one place: the landing page. The board header loses its project selector and goal picker, the More menu loses its owner and goal rows (**Sort by owner** moves into View), and the warning icons stop filtering: pressing one opens it to name what it counts, which is how a phone reads it, and pressing it again closes it. The chips under the header still say what the landing page chose, and **Change** leads back to it. Search and Focus stay on the board. `ProjectSelector` and `GoalFilterSelect` are deleted.
- The landing page's filters are four rows: Project, Goal, Owner and Stage. **Due by** (with its "Not done before" and "Archived before" modes and the date picker) and **New tasks** are gone; a stored choice from the older build keeps its four rows and drops the rest (`parseBoardFilters`). The board is always drawn from live tasks; the Archive page is where archived work is found.
- Closed things leave the filters. A goal that is done, abandoned or archived is no longer offered in the Goal row (`goalsOnOffer` in `lib/board-filters.ts`), as archived projects and owners already were not. A goal that closes while chosen stays on offer, still ticked, until it is unticked; one that is archived, binned or falls outside the chosen projects is let go, on the landing page and on the board alike (`usePruneChosenGoals`), so nothing can narrow the board without a box to untick it. Admin's Projects and Owners cards say that archiving takes one out of the filter page.
- The horizontal board layout no longer leaves an empty band above the bottom nav: its columns (and the preview pane) run down to a gutter's width of the nav at any viewport height. The band was padding — the shell reserved a guessed 5rem for a nav that is fixed over it, and the board's scroll area added 7rem more beneath the columns, which the vertical layout needs as scroll run-off (so its last card can clear the selection toolbar and toasts that float above the nav) but the horizontal layout, whose columns scroll inside themselves, cannot use. The nav is now the last child of the viewport-height shell instead of a fixed overlay, so the board takes exactly the height the nav leaves, whatever the nav's own height is (its credit line, a safe-area inset), and the 7rem run-off applies to the vertical layout only. The `bottom-nav` spacing token is gone.
- The board's Goals button is always there. Under "All projects" it used to vanish — the bottom nav on a phone showed Filing, Add, More, Bin with a gap where Goals belonged, and the header had no target button from `lg` — because the goals view had nowhere to go without a project. `/projects/all` is now the goals view across every project: the same cards, each with its project's chip (the key where it has one, the name otherwise), and the loose building-blocks counted across the board. `/projects/none` and `/projects/<id>` are unchanged. The shared `goalsInProject` and `unassignedBlocks` helpers take a project scope (`'all'`, `'none'` or a project id) instead of a project id or `null`.
- The stage-count chips above the board ("BACKLOG 3", "IN PROGRESS 1", …) are gone on every screen: each column already names its stage and count, and the row they led cost more than it said. The board warnings are icons now, each kind with its own glyph — a layered stack for too many in progress, a warning triangle for high-priority waiting, a clock for overdue, an hourglass for stale — in the tone the matching card borders use. The name, count and full sentence appear on hover (or keyboard focus), and pressing an icon, which filters the board as before, opens it to show its name and count, which is how a phone, with no hover, reads it. `StageHeaders` is removed.
- On a phone the board's top bar is the project selector's: the logo, then the selector filling the rest of the row, then the search toggle. The Goals and More buttons that shared the bar moved into the bottom nav — Filing, Goals, Add, More, Bin — where More is labelled like its neighbours. From the tablet breakpoint (`lg`, 768px) nothing moves: Goals and More stay in the header and the bar keeps its three. Neither bar can wrap, overlap or spill at any width now: the nav's buttons are sized so five of them fit a 320px screen and spread evenly about the centre; the wide header row no longer wraps either — the search field flexes between 8rem and 26rem and the title, project and goal labels truncate before anything is pushed to a second line. On a phone the filter chips and the warning pills sit centred too, the pills scrolling from the left only once they are wider than the screen.
- The phone UI is decluttered. This app's Tailwind `sm` is 375px, so layouts meant for tablets were applied on every phone; goal cards, the dependency pickers, the goal-plan and bulk-edit dialogs and the toast viewport now switch at `lg`. The edit dialog has one footer row (More, Cancel, Save), with History, Share, the goal plan and Delete (still confirmed) in its More menu, and priority, type, dependencies and effort in a collapsible section with a one-line summary. On a phone the goal filter is reachable from the More menu, active filters and warning pills show in a filter strip, the selection toolbar fits the screen, the last card clears the bottom nav and toasts sit above the nav. Buttons, the dialog close and header controls are 44px on phones. Deleting a stage or sub-stage in Admin now asks first (it deleted immediately before), Admin's icon buttons have names, the 404 page leads back to the board, pages have a title and the owner picker has an accessible name.
- One state per task: `tasks.status` is gone, and a task's state is the kind of the column it sits in (EPIC-03 stories 1 and 2). Two state machines used to run side by side and could contradict each other — the board drew `stage_id` while an agent filtering `status` got a different set, and the export shipped a `statusConflict` flag per task to report the disagreement it was papering over. Stages carry a new `kind` (`backlog`, `in_progress`, `waiting`, `done`, `abandoned`), set explicitly in Admin and shown beside each column's order, which replaces `getStatusFromStageName` — a substring match over the column's editable display name, so renaming a column silently restated every task in it, and one that was wrong where nobody could see it, since "Abandoned" contains "done" and classified as done. `waiting` is a state in its own right for the first time; the old enum had no value for it and folded those tasks into backlog. The task edit form loses its Status dropdown (the Stage picker is the state, and each option names the state it means), creating a task in a Done column now creates a done task rather than a backlog one, a drag writes only the stage, and history records a move between columns instead of a status write the client had to remember to send. Migration `0014_stage_kind.sql` backfills each column's kind by name once, in SQL, with waiting and abandoned tested before done, records every assignment in `stage_kind_backfill_report` and renumbers duplicate `order` values; `0015_drop_task_status.sql` reconciles any task whose stored status disagreed with its column, writing the old value into the task's own `history` and into `task_status_backfill_report`, then drops the column. The export's `formatVersion` is now **2**: `tasks[].status` is gone, while `briefing.*[].storedStatus` and `.statusConflict` stay at null and false so the digest's shape does not move. An import file written before this change is still accepted — its `status` chooses a column of the matching kind rather than being stored.
- The board is restyled off neumorphism onto a flat register: white `#FFFFFF`, ink `#14181F` and one teal `#005F73` (dark: `#0F1419`, `#E8EDF1`, `#51B9CC`), Lexend at every size with tabular figures, 1px `#E3E6EA` hairlines where the bevel shadows were, a 6px radius, and shadow only where something floats. Summary circles keep their mechanic (size is effort, the ring is the warning state) as a flat fill and one ring, and destructive controls stay outlined until an alert dialog's confirm. ### Fixed
- Timestamps the database stamps itself are UTC on any Postgres server, not only on one whose own zone is UTC. Every timestamp column is `timestamp` without time zone and the app reads each one back as UTC, but `now()` — every `defaultNow()` column (`createdAt` on every table, `tasks.viewed_at`, `inbound_email_processing.updated_at`, …) and every `NOW()` in server SQL — was cast into the session's TimeZone, while a Date the app wrote went in as UTC. On a server set to another zone (the local Homebrew Postgres is `Pacific/Auckland`), a task created at 07:28Z came back from `GET /api/tasks` with `createdAt` 20:28Z: the landing page's inbox said mail had arrived "in 13 hours", a new task was created 13 hours after it was last updated, and the inbound worker took a lease as expired 13 hours early. Every connection the server opens now runs its session in UTC (`server/pg-config.ts`, startup option `-c TimeZone=UTC`, after any `PGOPTIONS`). The migrator reads the server's own zone first, logs it at start-up (`Database server TimeZone is …`), and then pins its session too, so a migration's `DEFAULT now()` fills rows in UTC. Migration `0025_utc_timestamps.sql` moves the values already stored in local time to UTC — the columns only `now()` writes, and `updated_at` where it still equals `created_at` — records each one in `utc_timestamp_repair_report`, and changes nothing on a server whose zone is UTC. `copyAttachment` reads the `created_at` its raw query returns as UTC rather than in Node's zone.
- A new stage keeps the kind it is created with. `createStage` built its insert from the name, order and colour only, so `kind` fell to the column default and every stage created since `stages.kind` arrived (EPIC-03, 13 Oct) was stored as `backlog`, whatever was asked for: on a fresh database the seeded In Progress and Done columns were backlog, so the Done column drew as an ordinary column and its tasks counted as open work, and a column added from Admin lost the kind chosen in its form. Editing a stage's kind afterwards was not affected. Stages that existed before migration `0014` got their kind from that migration's backfill and are not affected either; a stage created since then that should not be backlog can be found by its missing row in `stage_kind_backfill_report` and corrected in Admin.
- Dictation stops when its field (a `VoiceInput` or the rich-text editor) loses focus, and when the page is blurred, hidden or navigated away from, so the microphone is released. It was reported on Android to keep listening after a tap outside the field (#153; not reproduced before the fix).
- The Predecessors/Successors picker scrolls inside the edit dialog. It is portalled outside the dialog, whose scroll lock swallowed wheel and touch events; the list now stops them propagating, uses `overscroll-contain` and caps its height to the space available.
- A summary circle's hover preview no longer covers drop targets and neighbouring cards during a drag. It is suppressed while any drag is active, closes on pointer down, ignores pointer events, opens above the circle inside the viewport after 500 ms (was 300), and the duplicate native `title` tooltip is an `aria-label` instead.
- The Admin project row's short-code and Archived badges sit beside the name again. They were `<div>`s inside a `<p>`, which the browser closed early (React logged `validateDOMNesting`); the row is a `<div>` now.
- The "Stale tasks" pill no longer counts finished work. `stale` was the only board warning with no closed-task gate, so a card sitting untouched in a Done column for a fortnight was reported as neglected — on the dev board, six done tasks untouched for 47–63 days made the pill read "Stale tasks 6" over a board with nothing to do. It now applies the same closed check `overdue` already applied, and so does the matching card border, which had the same defect. Archived and binned tasks are also excluded explicitly rather than only by never reaching the board's list.
- A database created from the migrations alone now gets `inbound_email_processing.created_task_ids` and the `ON DELETE SET NULL` foreign key. The files `0005_inbound_email_created_task_ids.sql` and `0006_fk_created_task_id_set_null.sql` were never registered in `migrations/meta/_journal.json`, so the migrator skipped them: on a fresh database "Delete forever" on a task failed with `column "created_task_ids" does not exist`. Both are folded into the idempotent `0012_inbound_email_created_task_ids.sql`, which is a no-op on a database that already got the column another way.
- `GET /api/export` no longer serves a cached snapshot: every response sends `Cache-Control: no-store, no-cache, must-revalidate` and `CDN-Cache-Control: no-store`, so two fetches of the same URL return different `exportedAt` values. A briefing agent polling the identical URL had been replayed the same 12-hour-old body until a junk query parameter forced a rebuild. (BUG-003)
- Export day boundaries are cut in `Pacific/Auckland` rather than the server's UTC, so `generatedFor`, `daysOverdue`, `dueBucket` and the overdue/dueToday buckets are right during NZ mornings, when UTC is still on the previous date. `?tz=` accepts any IANA zone, defaulting to `Pacific/Auckland`; an unknown zone is a 400, and `overdueRule` names the zone actually used. (BUG-003)
- Export entries carry `dueDay`, the card's labeled calendar date (YYYY-MM-DD), on both `tasks[].urgency` and every `briefing` entry. The date picker stores a due date as the chosen day at local midnight, so the `dueDate` instant's UTC date part is a day earlier than the label — a consumer reading a date out of that instant saw every card a day early. `overdueRule` now names `dueDay` as the field to compare. (BUG-004)

### Changed
- The board's overdue highlight, the card's printed due date and the export's `overdue` list all derive from one helper (`dueDayFor` / `isOverdueOn` in `shared/briefing.ts`) instead of browser-local `isPast`/`isToday`, so board and export cannot disagree. A card's day is now the board's zone rather than the viewer's, so due dates no longer shift when the board is opened from another timezone. (BUG-004)
